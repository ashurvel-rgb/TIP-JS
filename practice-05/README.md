**Вариант:** 8

## Цель работы

Реализовать HTTP-клиент на основе `fetch`, передавать фильтры в query-параметрах, проверять ответы API и различать HTTP-, сетевые, форматные ошибки, тайм-аут и отмену запроса.

## Окружение и запуск

- Windows 11 10.0.22000;
- Node.js v24.22.1.

```bash
npm start
npm run client
npm test
```

API запускается по адресу `http://127.0.0.1:5505/api`.

## Реализация

- `buildUrl` нормализует базовый адрес, соединяет путь и кодирует непустые query-параметры;
- `requestJson` выполняет GET с заголовком `Accept: application/json`, тайм-аутом и внешним `AbortSignal`;
- HTTP-статус проверяется до проверки `Content-Type`, поэтому ответ 404 остаётся HTTP-ошибкой;
- `createTaskApi` проверяет фильтры и схему задач и категорий;
- задачи и категории загружаются параллельно через `Promise.all`.

## Результаты проверок

| Набор | Результат |
|---|---:|
| Контракт учебного API | 18 из 18 |
| Модульные проверки клиента | 26 из 26 |
| Интеграционные проверки | 13 из 13 |

Контрольный запрос `{ completed: false, priority: "high" }` возвращает id `[4, 13, 34]` и `meta.total = 3`. Запрос задачи 999 обрабатывается как `ApiError` с `kind: "http"` и `status: 404`.

## Индивидуальный вариант

Для варианта 8 используются фильтры:

```js
{ completed: false, priority: "high", categoryId: 2 }
```

Сформированный адрес содержит все три query-параметра. Получены задачи `[4, 34]`, `meta.total = 2`, что соответствует таблице вариантов.

## Собственные сценарии

1. Поиск `q=провер` возвращает id `[7, 16]` и подтверждает кодирование строки.
2. `/debug/text` возвращает неожиданный тип содержимого и преобразуется в `invalid-response`.
3. Задержка 150 мс при тайм-ауте 20 мс преобразуется в `timeout`, а явный `AbortController.abort()` — в `aborted`.

## Вывод

Клиент изолирует сетевой слой от прикладного API, сохраняет структурированные сведения об ошибках и проверяет данные до передачи вызывающему коду.
